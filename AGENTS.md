# Долгосрочная цель

Разработать CommandLineMCP — систему выполнения команд командной строки по заданиям от LLM. Система состоит из двух частей: MCP-сервера и клиента-исполнителя.

## Архитектура и поток задания

1. LLM передаёт команду MCP-серверу через MCP-инструмент.
2. Сервер сохраняет задание в базе данных, присваивает ему уникальный идентификатор и связывает с клиентом, которому оно предназначено.
3. Клиент самостоятельно опрашивает сервер и получает предназначенные ему задания.
4. Клиент выполняет команду в своём окружении.
5. Клиент отправляет серверу результат выполнения с идентификатором задания.
6. Сервер сохраняет результат в базе данных и предоставляет его LLM через MCP.

Сервер отвечает за приём, хранение и выдачу заданий и результатов. Команды выполняются на стороне клиента. Инициатором получения заданий и отправки результатов является клиент.

## Согласованные технологии

- Сервер: C#, развёртывание в Docker-контейнере.
- Клиент: простая программа на Python, которая получает задания от сервера, выполняет их и отправляет результаты обратно.
- При выборе зависимостей и способа развёртывания стремиться к легковесному решению.
- База данных: SQLite, файл хранится в папке хоста, примонтированной в контейнер через bind mount. Отдельный именованный Docker volume для базы не использовать.
- LLM подключается к серверу через MCP по HTTP. Клиент использует отдельный HTTP API с long polling.

## Аутентификация

- Сервер многопользовательский. У каждого пользователя свои клиенты, задания и результаты. OAuth-идентичность связывается с пользователем сервера; сервер проверяет принадлежность клиентов, заданий и результатов при каждом обращении. Пользователь не получает доступ к данным и машинам других пользователей.
- Клиент передаёт Bearer-ключ из локального конфигурационного файла (INI/config или аналог). На сервере учёт ключа хранится в базе данных и связывается с конкретным клиентом; предпочтительно хранить проверочный хеш вместо открытого секрета.
- Доступ ChatGPT к MCP защищается OAuth, совместимым с подключением пользовательского MCP-сервера в ChatGPT. Не подменять OAuth статическим API-ключом или анонимным доступом.
- Предусмотреть OAuth 2.1 authorization code flow с PKCE S256, discovery metadata, привязку токена к ресурсу MCP и проверку токенов и прав на сервере.
- Конкретный провайдер ещё не выбран. Telegram предложен пользователем как возможный способ входа; совместимость выбранной схемы с MCP OAuth нужно проверить отдельно.

## Выполнение и результаты

- Основная оболочка клиента: Windows PowerShell. Предусмотреть extension point для Windows cmd и оболочек Linux; их реализация не является обязательной частью первой версии.
- Клиент выполняет любые полученные команды с правами запустившего его пользователя, включая разрушительные. Фильтрация команд, подтверждения и оценка последствий не являются обязанностью клиента.
- В первой версии клиент выполняет одну команду одновременно. Задание содержит рабочую директорию и таймаут.
- Результат содержит stdout, stderr и код завершения, связан с идентификатором задания.
- Клиент сохраняет результат локально и повторяет отправку при обрывах связи. Повторная отправка результата не должна создавать дубликаты.
- Если клиент пропал во время выполнения, исход считается неизвестным. Не запускать такую команду автоматически повторно: действие могло уже выполниться.
- Постановка задания через MCP сразу возвращает его ID. Отдельный MCP-инструмент позволяет проверить состояние или ограниченное время ждать результата.

## Требования к дальнейшей проработке

- Сохранять связь между командой, клиентом, идентификатором задания, состоянием выполнения и результатом.
- В результате предусмотреть стандартный вывод, стандартный поток ошибок и код завершения команды.
- Уточнить провайдера OAuth и процедуру регистрации клиентов и выдачи их ключей владельцам. Версии .NET и Python пока не выбраны.
- Не считать ещё не согласованные технические решения частью утверждённой архитектуры.

## Границы текущего этапа

Сейчас зафиксированы цель, базовая схема взаимодействия и языки сервера и клиента. Реализация и оставшиеся технические решения — последующие этапы по указанию пользователя.
