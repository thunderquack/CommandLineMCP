# Долгосрочная цель

Разработать CommandLineMCP — систему выполнения команд командной строки по заданиям от LLM. Система состоит из двух частей: MCP-сервера и клиента-исполнителя.

## Архитектура и поток задания

1. LLM передаёт команду MCP-серверу через MCP-инструмент.
2. Сервер сохраняет задание в базе данных, присваивает ему уникальный идентификатор и связывает с клиентом, которому оно предназначено.
3. Клиент самостоятельно опрашивает сервер и получает предназначенные ему задания.
4. Клиент выполняет команду в своём окружении.
5. Клиент отправляет серверу результат выполнения с идентификатором задания.
6. Сервер сохраняет результат в базе данных и предоставляет его LLM через MCP.

Сервер отвечает за приём, хранение и выдачу заданий и результатов. Команды выполняются на стороне клиента. Инициатором получения заданий и отправки результатов является клиент.

## Согласованные технологии

- Сервер: C#, развёртывание в Docker-контейнере.
- Клиент: простая программа на Python, которая получает задания от сервера, выполняет их и отправляет результаты обратно.
- При выборе зависимостей и способа развёртывания стремиться к легковесному решению.
- База данных: SQLite, файл хранится в папке хоста, примонтированной в контейнер через bind mount. Отдельный именованный Docker volume для базы не использовать.
- LLM подключается к серверу через MCP по HTTP. Клиент использует отдельный HTTP API с long polling.

## Аутентификация

- Сервер многопользовательский. У каждого пользователя свои клиенты, задания и результаты. OAuth-идентичность связывается с пользователем сервера; сервер проверяет принадлежность клиентов, заданий и результатов при каждом обращении. Пользователь не получает доступ к данным и машинам других пользователей.
- Клиент передаёт Bearer-ключ из локального конфигурационного файла (INI/config или аналог). На сервере учёт ключа хранится в базе данных и связывается с конкретным клиентом; предпочтительно хранить проверочный хеш вместо открытого секрета.
- Доступ ChatGPT к MCP защищается OAuth, совместимым с подключением пользовательского MCP-сервера в ChatGPT. Не подменять OAuth статическим API-ключом или анонимным доступом.
- Предусмотреть OAuth 2.1 authorization code flow с PKCE S256, discovery metadata, привязку токена к ресурсу MCP и проверку токенов и прав на сервере.
- Способ входа пользователей: Telegram. Вход через Telegram должен быть интегрирован в полноценный OAuth-поток для ChatGPT; сам по себе вход через Telegram не заменяет MCP OAuth. Конкретную техническую интеграцию и совместимость проверить при реализации.

## Веб-страница управления

- Предусмотреть небольшую веб-страницу сервера со входом через Telegram.
- После входа пользователь может создавать своих клиентов и получать Bearer-ключи для их локальных конфигурационных файлов.
- Пользователь может отзывать ключи своих клиентов. Управление чужими клиентами недоступно.

## Выполнение и результаты

- Основная оболочка клиента: Windows PowerShell. Предусмотреть extension point для Windows cmd и оболочек Linux; их реализация не является обязательной частью первой версии.
- Клиент выполняет любые полученные команды с правами запустившего его пользователя, включая разрушительные. Фильтрация команд, подтверждения и оценка последствий не являются обязанностью клиента.
- В первой версии клиент выполняет одну команду одновременно. Задание содержит рабочую директорию и таймаут.
- Результат содержит stdout, stderr и код завершения, связан с идентификатором задания.
- Клиент сохраняет результат локально и повторяет отправку при обрывах связи. Повторная отправка результата не должна создавать дубликаты.
- Если клиент пропал во время выполнения, исход считается неизвестным. Не запускать такую команду автоматически повторно: действие могло уже выполниться.
- Постановка задания через MCP сразу возвращает его ID. Отдельный MCP-инструмент позволяет проверить состояние или ограниченное время ждать результата.

## Требования к дальнейшей проработке

- Сохранять связь между командой, клиентом, идентификатором задания, состоянием выполнения и результатом.
- В результате предусмотреть стандартный вывод, стандартный поток ошибок и код завершения команды.
- Выбрать техническую реализацию OAuth с входом через Telegram. Версии .NET и Python пока не выбраны.
- Не считать ещё не согласованные технические решения частью утверждённой архитектуры.

## Техническая база серверного каркаса

- Текущий серверный каркас использует .NET 11 и EF Core 11.
- Контекст EF Core и миграции размещаются в отдельном проекте `CommandLineMcp.Data` на .NET 11.
- SQLite-файл по умолчанию: `Data Source=data/commandline-mcp.db`; строку подключения можно переопределить через `ConnectionStrings__Database`.
- Новые таблицы предметной области добавлять только по отдельному указанию пользователя.
- OAuth реализован через OpenIddict с Telegram OIDC (`https://oauth.telegram.org`): callback `/auth/telegram/callback`, вход на `/login`, согласие на `/connect/authorize`, выдача токенов `/connect/token`, отзыв `/connect/revoke`. OAuth authorization-code использует PKCE S256; разрешён ресурс `https://cmd.example.com/mcp`, issuer `https://cmd.example.com/`, scope `commands` и опционально `offline_access` для refresh-токенов.
- MCP protected-resource metadata доступна на `/.well-known/oauth-protected-resource/mcp`; authorization-server metadata публикует динамический `registration_endpoint` `/register`. DCR создаёт клиентов с секретом, который возвращается только в ответе регистрации. Не подменять регистрацию вручную заданным секретом ChatGPT.
- Секреты читаются из `/run/secrets/server.secrets.json` (путь переопределяется `OAuth__SecretsFile`): `OAuth:SigningCertificate:PfxBase64`, `OAuth:SigningCertificate:Password`, `Telegram:ClientId`, `Telegram:ClientSecret`. `secrets/server.secrets.json` игнорируется Git; пример хранится в `secrets/server.secrets.example.json`. CLI `auth init-secrets [path]` создаёт самоподписанный OAuth signing/encryption PFX и случайный пароль. Этот сертификат не является TLS-сертификатом публичного reverse proxy.
- Data Protection key ring хранится в `/data/keys` и защищён OAuth PFX. Reverse proxy обязан передавать HTTPS scheme/host. По умолчанию forwarded headers принимаются только от явных `ForwardedHeaders:KnownProxies` адресов. Для deployment, где общая Docker-сеть намеренно является границей доверия, можно явно включить `ForwardedHeaders:TrustAllProxies=true`; настройка отключена по умолчанию.
- Telegram OIDC login автоматически создаёт отсутствующего пользователя с `IsOAuthAllowed=false`, `RoleId=0`; такому пользователю вход запрещён. Административный `users allow-oauth <TelegramId...>` создаёт отсутствующих пользователей сразу с OAuth enabled и `RoleId=0`. Роль `0` остаётся базовой.
- Административный CLI размещается в отдельном проекте `CommandLineMcp.Admin`, включённом в Docker-образ сервера по пути `/app/admin`; команды адресуются по конкретным Telegram ID.
- Успешные пакетные изменения CLI выполняются атомарно; повторная установка уже действующего OAuth/RoleId не должна менять `UpdatedAt`.
- Для крупных задач реализации явно задействовать Luna subagents для независимых частей; интеграцию и итоговую проверку выполнять централизованно.
- EF Core запросы и операции с базой разрешены только классам проекта `CommandLineMcp.Data`; composition root может регистрировать и конфигурировать DbContext. Серверные endpoints, background workers и Admin CLI обращаются к данным через интерфейсы репозиториев/обслуживания из Data. Не раскрывать `IQueryable` или EF-типы через эти интерфейсы и не выполнять raw SQL.
- При модульных тестах потребителей подменять репозитории mock-объектами. Сохранять SQLite integration tests для проверки реализации репозиториев и схемы.

Сейчас зафиксированы цель, базовая схема взаимодействия и языки сервера и клиента. Реализация и оставшиеся технические решения — последующие этапы по указанию пользователя.
